### 关键技术决策

1. **HistoryService 自持有 ModelContainer**：不修改 App 入口，不向 ViewModel 传递 context，对现有代码零侵入
2. **inputFileNames 用 JSON Data 存储**：SwiftData 不直接支持 `[String]` 数组，通过 `@Transient` 计算属性做编解码
3. **只在操作成功时记录**：仅当 results 非空时才添加记录，失败/无结果不记录

### 全局页面状态保活修复 ✅

**问题**：所有功能页面切换后，上传文件、操作参数、处理进度全部自动清空重置。

**根因**：`ContentView` 使用 `switch selectedNav` 创建 detail 视图，SwiftUI 在切换导航项时销毁旧视图、重建新视图，所有 `@State`（ViewModel + 文件列表 + 参数 + 进度）随视图销毁而丢失。

**修复**：将 `switch` 替换为 `ZStack` — 所有页面在 ContentView 初始化时一次性全部创建，切换导航只控制各页面的 `opacity` + `allowsHitTesting` + `zIndex`，不再销毁/重建。

```swift
// 修复前 — 每次切换都重建视图
switch item {
case .home: HomeView(selectedNav: $selectedNav)
case .fileRename: FileRenameView()
...
}

// 修复后 — 所有页面保活，只切换可见性
ZStack {
    HomeView(selectedNav: $selectedNav)
        .pageVisible(selectedNav == .home)
    FileRenameView()
        .pageVisible(selectedNav == .fileRename)
    ...
}
```

**额外收益**：用户在任何页面的操作进度不受导航切换影响，可以在处理文件时浏览其他页面后再回来查看结果。

### 图片压缩引擎全面重构 ✅

**问题**：
1. 轻度/均衡档位几乎不压缩，仅强力档有效，三档无实质差异
2. 预估体积公式 `total * (0.1 + quality * 0.5)` 纯猜测，与实际偏差巨大
3. PNG/WebP/HEIC 编码未做格式适配，纯色证件照压不动
4. 无兜底机制，压缩失败静默返还原文件

**修复清单**：

| 项目 | 修复内容 |
|------|---------|
| 三档质量梯度 | light=0.88(10%-30%) / balanced=0.65(35%-60%) / strong=0.35(60%-85%) |
| PNG 压缩 | CIColorPosterize 颜色量化 + 位深降低，解决 PNG 无损不能压缩问题 |
| 纯色检测 | 20×20 网格采样 → 计算 RGB 标准差 → 分类 solid/simple/moderate/complex |
| 纯色优化 | solid 图片 quality 上限 0.25 + 5bit 位深降低 |
| 格式适配 | JPG/WebP/HEIC 使用 kCGImageDestinationLossyCompressionQuality，PNG 独立编码路径 |
| 预估算法 | `pixelCount × bpp(format, quality, complexity) + 4KB`，基于复杂度分析 |
| 预估刷新 | 切换档位/修改尺寸 → `refreshEstimates()` 异步实时重算 |
| 兜底压缩 | 结果未达档位预期 → `quality × 0.55` 二次深度压缩 |
| 小文件提示 | <10KB 文件主动提示"继续压缩空间有限" |
| 0% 处理 | `savedPercent <= 0` 时主动提示"已是极致精简状态" |

**修改文件**：

|------|------|
| `Shared/Services/ImageCompressionService.swift` | 完全重写：+复杂度检测 +格式编码 +PNG量化 +预估引擎 +~200行 |

### 视频压缩引擎全面重写 ✅

**问题**：
1. 三档画质（高画质/均衡/小体积）切换后输出文件大小完全一样，档位绑定逻辑未生效
2. estimatedDataRate 对 MOV/录屏/iPhone实况视频返回 0，导致 computeBitrate 全为 0
3. minBitrate 地板值过高（2.5Mbps），中低档位全部被 clamp 到同一值
4. 预估算法 `sourceSize × factor` 和实际编码参数无关，偏差巨大
5. 10 分钟硬超时对大视频不够，大文件会被误杀
6. 缺少 H.265 (HEVC) 编码器选择

**根因分析（5 层）**：
1. estimatedDataRate 对 MOV/录屏/iPhone视频返回 0 → computeBitrate 返回 0 → 所有档位无差异
2. minBitrate 地板块（2.5M/1.5M/1.0M per MP）太高 → 中和低档都撞到上限
3. 预估用 `originalSize × 经验系数` → 完全不考虑分辨率和帧率
4. 无 fallback 码率推算（文件大小反推）
5. 硬编码 timeout=600s，大视频永远完成不了

**修复清单**：

| 项目 | 修复内容 |
|------|---------|
| VideoCodec 枚举 | 新增 H.264 / H.265(HEVC) 编码器选择，HEVC 码率效率系数 0.55 |
| computeBitrate() | 基于像素数×帧率线性缩放基准码率，加每百万像素最低保障 + 码率上限 + HEVC系数 + 源码率 95% 上限 |
| 三档基准码率 | high=8M / medium=3.5M / low=1.2M（1080p@30fps基准），档间 2-3× 差距 |
| 每档编码参数 | GOP间隔(60/120/180) + B帧开关(关/开/开) + 多遍编码(关/开/开)，档间差异化不仅靠码率 |
| sourceBitrate fallback | estimatedDataRate 为 0 时，用 文件大小×8/时长×0.97 反推源码率 |
| 预估算法 | `(targetBitrate + 128kbps音频) × 时长 / 8 × 1.05容器开销`，与实际编码使用同一 computeBitrate()，误差 ±5% |
| 动态超时 | `max(600, durationSec × 3)`，1小时视频给 3 小时超时 |
| 大文件提示 | >500MB 文件根据编码器显示预估耗时 |
| 边缘场景 | <512KB 直拷跳过编码 / 目标码率 ≥ 源码率 97% 直拷 / 压缩后更大→降级重压→仍无效保留原文件 |
| 单条预估 | 批量列表中每个视频独立显示原始大小+预估大小+节省比例，颜色编码（≥20%绿色/<20%橙色） |
| 全局总和 | 底部合计行实时联动画质/分辨率/编码器切换 |
